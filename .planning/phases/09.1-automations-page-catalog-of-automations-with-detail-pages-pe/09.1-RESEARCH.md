# Phase 09.1: Automations Page — Research

**Researched:** 2026-08-08
**Domain:** Multi-offering product page catalog with dynamic routing, component reuse across offerings, route migration from Phase 7
**Confidence:** HIGH (patterns verified in existing codebase, Next.js standards, locked decisions in UI-SPEC and CONTEXT.md)

## Summary

Phase 09.1 transforms `/automate` from a single-product detail page (offering #1, Instagram) into a catalog page listing 5 automation offerings, each linking to its own dynamic detail page. The phase reuses the Phase 7 page component pattern (`HeroSection`, `PricingSection`, `ComparisonStrip`, etc.) for each offering's detail page, with locked pricing, copy constraints, and a new breadcrumb navigation pattern.

**Critical path item:** The route migration from `/automate` (Phase 7 offering #1 detail) to `/automate/[slug]` dynamic routing requires a backwards-compatibility decision—redirect old `/automate` links to `/automate/instagram`, or let them land on the new catalog. The decision affects URL architecture, Plausible analytics event tracking, and whether old Reel links continue to serve the Instagram offering or the catalog entry point.

**Primary recommendation:** Implement a Next.js `[slug]` dynamic route segment to serve all five offerings. Add a redirect in `next.config.mjs` from `/automate` → `/automate/instagram` for backwards compatibility with Phase 7 Reel links. Extend `checkout.ts` with an `offerings` metadata array (mirroring the `automateTiers` pattern) to store per-offering data. Reuse Phase 7 components with offering-specific props. Keep the route group `(automate)` and isolated layout intact.

### Pattern 1: Next.js Dynamic Route Segment `[slug]`

**What:** Next.js App Router captures URL path segments as parameters and passes them to the page component. The `[slug]` segment matches any path and extracts the parameter.

**When to use:** For multi-offering detail pages where the URL structure is `/automate/[offering-slug]` and the offering ID drives which content to render.

**Example:**

```typescript
// src/app/(automate)/[slug]/page.tsx
// Source: Next.js App Router documentation + existing codebase pattern

import { notFound } from "next/navigation";
import type { Metadata } from "next";
import { offerings } from "@/lib/checkout";
import HeroSection from "@/components/automate/HeroSection";
import ComparisonStrip from "@/components/automate/ComparisonStrip";
import PricingSection from "@/components/automate/PricingSection";
import FAQSection from "@/components/automate/FAQSection";
import Breadcrumb from "@/components/automate/Breadcrumb";
import type { OfferingSlug } from "@/lib/checkout";

export const dynamicParams = false; // Pre-render only known slugs; 404 for unknown

// Generate static params for all known offerings (builds all 5 at compile time)
export async function generateStaticParams() {
  return Object.keys(offerings).map((slug) => ({
    slug,
  }));
}

// Generate metadata per offering
export async function generateMetadata({
  params,
}: {
  params: { slug: string };
}): Promise<Metadata> {
  const offering = offerings[params.slug as OfferingSlug];
  if (!offering) return {};
  
  return {
    title: `${offering.name} | Asor Ahura`,
    description: offering.description,
  };
}

export default function OfferingPage({ params }: { params: { slug: string } }) {
  const offering = offerings[params.slug as OfferingSlug];
  
  if (!offering) {
    notFound(); // Renders the 404 page
  }

  return (
    <>
      <Breadcrumb offeringName={offering.name} />
      <HeroSection offering={offering} />
      <ComparisonStrip offering={offering} />
      <PricingSection offering={offering} />
      <FAQSection offering={offering} />
    </>
  );
}
```

### Pattern 4: Route Migration Strategy — Backwards Compatibility

**What:** Redirect old `/automate` requests to `/automate/instagram` so Reel links and analytics events from Phase 7 continue to serve the Instagram offering without breaking.

**When to use:** When changing a route's meaning (e.g., from "detail page" to "catalog") and old links need to keep working.

**Example:**

```typescript
// next.config.mjs — ADD to existing redirects() array
// Source: Next.js redirects documentation

async redirects() {
  return [
    {
      source: '/flowmorph',
      destination: '/',
      permanent: true,
    },
    // NEW: Backwards compatibility for Phase 7 Reel links
    {
      source: '/automate',
      destination: '/automate/instagram',
```

**Alternative: No redirect, let catalog be the entry point**

If the decision is to let old `/automate` Reel links land on the new catalog instead (and let users navigate to Instagram from there), skip the redirect. However, this breaks backwards compatibility and may confuse users expecting the Instagram detail page.

### Anti-Patterns to Avoid

- **Hardcoding offering names/slugs in components:** Use the offerings metadata array; parametrize all offering-specific content
- **Separate implementation per offering:** Reuse HeroSection, PricingSection, etc. with offering-specific props; don't rebuild components per offering
- **Forgetting to update hardcoded `/automate` links:** All internal links (success page, emails, etc.) must either stay generic (work with both old and new routes) or explicitly redirect
- **No error handling for unknown slugs:** Use `notFound()` in dynamic route if slug is not in the offerings array; generates a proper 404 page
- **Mixing offering data in component files:** All pricing, names, descriptions belong in lib/checkout.ts, not in TSX

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Multi-offering catalog routing | Custom routing logic with string matching | Next.js App Router `[slug]` dynamic segment | Built-in, handles path params, SEO metadata generation, static generation strategies |
| Pagination or filtering offerings | Custom filter/sort state machine | Static grid + optional JavaScript filtering | 5 offerings fit on one page; no pagination needed per UI-SPEC |
| Offering data structure | Scattered props, inline objects per component | Centralized `offerings` array in lib/checkout.ts | Single source of truth; enables reuse across catalog, detail pages, nav |
| Backwards-compatible redirects | Manual link rewriting or client-side navigation | Next.js `redirects()` in next.config.mjs | Preserves SEO, handled at build time, atomic with deployment |
| Breadcrumb links | Hardcoded `<a>` tags per page | Reusable `<Breadcrumb>` component | DRY, maintainable, tested once, styled consistently |
| Conditional checkout rendering (offering #1 vs. waitlist) | Large if/else chains in PricingSection | Pass offering metadata to PricingSection; render based on `offering.hasLiveCheckout` | Clearer logic, testable, scales to future checkout-enabled offerings |

## Common Pitfalls

### Pitfall 1: Forgetting to Update the Success Page Return Link

**What goes wrong:** The success page at `/automate/success` has a hardcoded link `href="/automate#pricing"` pointing to the old route. When `/automate` becomes the catalog, this link is broken or points to the wrong section.

**Why it happens:** The link was authored when `/automate` was the detail page with a `#pricing` section. The catalog page also has `#pricing` (in the FAQ or top-level intro), but the intent was to return the buyer to the pricing section of the offering they just bought (Instagram), not the catalog.

**How to avoid:** 
1. Update the success page link to point to the detail page directly: `href="/automate/instagram#pricing"` (for offering #1)
2. Or, change it to just `href="/automate"` and let the catalog be the entry point
3. For offerings 2–5 (when they get success pages), point to their respective detail page: `href="/automate/email-triage#pricing"`, etc.

**Warning signs:** Existing hardcoded `/automate` links in emails, success pages, or components that should point to a specific offering detail page.

### Pitfall 2: Analytics Event Tracking Breaks After Route Migration

**What goes wrong:** Plausible events tagged with `/automate` path now have mixed meanings — some are from the old detail page (offering #1), some are from the new catalog. Historical data becomes ambiguous.

**Why it happens:** The route change is permanent; old Reel events and new catalog events both fire on `/automate` (if no redirect) or one continues to fire on the old path (if redirect is enabled).

**How to avoid:**
1. **If using a redirect** (`/automate` → `/automate/instagram`): analytics will cleanly separate old and new data. Old Reel clicks redirect to `/automate/instagram`, newer events are on `/automate` (catalog) and `/automate/[other-slugs]` (other offerings).
2. **If NOT using a redirect** (old links land on catalog): explicitly document in Plausible analytics documentation that `/automate` changed meaning on the date Phase 09.1 shipped. Filter historical data by date if needed.
3. **Verify Plausible goals/events:** If custom events are tied to path (e.g., "Land on /automate"), check if they auto-update or need manual adjustment.

**Warning signs:** Gaps in event tracking after deployment; events on `/automate` before Phase 09.1 vs. after showing different behavior.

### Pitfall 3: Forgetting Metadata Generation for Dynamic Routes

**What goes wrong:** The `/automate/[slug]` pages are indexed by search engines with generic or incorrect metadata (title, description, og:image), hurting SEO.

**Why it happens:** Dynamic routes require explicit `generateMetadata()` function to create per-route metadata at build or request time. Without it, Next.js uses a default or inherits from the parent layout.

**How to avoid:**
1. Implement `generateMetadata()` in `/automate/[slug]/page.tsx` that pulls offering metadata and returns `Metadata` object
2. Include offering name, description, and unique title per offering
3. Test with `next build` to verify metadata is generated for all 5 offerings

**Warning signs:** Offering detail pages all showing the same title in search results; social media preview shows generic or placeholder text.

### Pitfall 4: Offering #1 Success Page Handling

**What goes wrong:** After purchasing offering #1, the success page at `/automate/success` now needs to know which offering was purchased (to render offering-specific onboarding copy and next-steps messaging). If the routing changes, the success page no longer receives context about which offering.

**Why it happens:** Phase 7's success page was hardcoded for offering #1 (Instagram). When offering #1 moves to `/automate/instagram`, the success page should move with it to `/automate/instagram/success` OR remain at a generic path but receive the offering ID as a parameter.

**How to avoid:**
1. **Option A: Keep offering #1 success page at existing location** (`/automate/success`), but ensure the Paddle webhook redirects to it with a product ID or slug parameter (e.g., `?product=instagram`)
2. **Option B: Move success page under offering #1's route** (`/automate/instagram/success`) — this is cleaner architecturally but requires careful redirect from old path
3. **Option C: Create a generic success page template** at `/automate/[slug]/success` for all offerings to reuse
4. For offerings 2–5 (future), ensure success pages receive offering context via URL param or route structure

**Warning signs:** Success page rendering generic content; product-specific copy missing (e.g., "Instagram handle" field not rendered for non-Instagram offerings).

### Pitfall 5: Padding Prices in Display

**What goes wrong:** Prices are displayed rounded (e.g., "$1,500" shown as "$1.5k" or "$1500") or approximated, violating the CONTEXT.md lock that requires exact figures.

**Why it happens:** Component authors abbreviate or round for aesthetic reasons, unaware of the pricing lock.

**How to avoid:**
1. Use `getOfferingBySlug()` or the offerings metadata array for all pricing display
2. Format currency using Intl.NumberFormat or a utility, but never round or abbreviate
3. Add a linter rule or component prop validation to catch unauthorized price changes
4. Document in CLAUDE.md: "All offering prices are locked per CONTEXT.md; do not round or abbreviate"

**Warning signs:** Price displays on catalog vs. detail pages not matching; Git diffs showing price changes that weren't requested.

## Next.js App Router Details

**Dynamic Route Segment Precedence:**

Next.js App Router prioritizes routes in this order:
1. Explicit routes (e.g., `/automate/instagram/page.tsx`)
2. Dynamic segment routes (e.g., `/automate/[slug]/page.tsx`)
3. Catch-all routes (e.g., `/automate/[...rest]/page.tsx`)

**Decision:** Use `[slug]` dynamic segment for offerings 2–5, and optionally keep `/automate/instagram/page.tsx` as an explicit route for offering #1 if it has unique layout or logic. Otherwise, let the `[slug]` route handle all 5 offerings.

**Static Generation:**

Use `generateStaticParams()` to pre-render all 5 offering pages at build time. This eliminates runtime lookups and improves performance.

```typescript
export async function generateStaticParams() {
  return [
    { slug: "instagram" },
    { slug: "email-triage" },
    { slug: "writing-constitution" },
    { slug: "rate-aware-invoice" },
    { slug: "client-onboarding" },
  ];
}
```

**Error Handling:**

Use `notFound()` to render the 404 page if an unknown slug is requested. This is cleaner than rendering an error boundary and improves SEO (404 is crawlable; error page is not).
