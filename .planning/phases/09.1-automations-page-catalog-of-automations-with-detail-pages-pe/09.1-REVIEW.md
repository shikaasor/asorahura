# Phase 09.1: Code Review Report

**Reviewed:** 2026-08-08
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

Reviewed the automations catalog page, the new dynamic offering detail route (`/automate/[slug]`), the Instagram success-page rename, the associated redirect and copy fixes, and the new `checkout.ts` offerings data module, plus the accompanying tests. No critical/security-severity bugs that are exploitable in the current production configuration were found — the app correctly relies on `dynamicParams = false` to keep the dynamic route closed to unlisted slugs, JSX renders all copy as text (no `dangerouslySetInnerHTML`), and the test suite locks in the pricing/copy/routing facts well.

That said, three real defects should be fixed before merge: a lookup helper (`getOfferingBySlug`) that returns `Object.prototype` for slugs like `"__proto__"` or `"constructor"` instead of `null` (currently masked only by `dynamicParams = false`, not defended in the function itself), an analytics event-naming collision that makes it impossible to distinguish "clicked the offering title" from "clicked the live-checkout CTA" for the Instagram card, and a hardcoded "5 automations" count in the offering detail page's back-link that will silently go stale the next time an offering is added or removed. A few smaller quality items (duplicate/dead metadata fields, an unnecessary `"use client"` directive, and a fragile string comparison in the order-notification email) are also flagged.

## Warnings

### WR-01: `getOfferingBySlug` returns `Object.prototype` (or its members) for prototype-name slugs instead of `null`

**File:** `src/lib/checkout.ts:308-310`
**Issue:** `offerings` is a plain object literal, so it inherits from `Object.prototype`. The lookup

```ts
export function getOfferingBySlug(slug: string): OfferingMetadata | null {
  return (offerings as Record<string, OfferingMetadata>)[slug] || null;
}
```

does a bracket-index lookup without an own-property check. For `slug` values such as `"__proto__"`, `"constructor"`, `"toString"`, or `"hasOwnProperty"`, `offerings[slug]` resolves to a truthy object (`Object.prototype`, the `Object` constructor, etc.) rather than `undefined`, so the `|| null` fallback never triggers. The function then returns something that is *not* an `OfferingMetadata`, and any caller that destructures fields off it (e.g. `OfferingDetailBody`'s `offering.faqs.map(...)`) would throw a `TypeError: Cannot read properties of undefined` at runtime instead of hitting the intended `notFound()` path.

In the current app this is masked because the `[slug]` route sets `dynamicParams = false` and `generateStaticParams` only emits the 4 waitlist slugs, so Next.js 404s before `getOfferingBySlug` is ever called with an attacker-controlled value. But the function is exported and has no such guarantee at the type/contract level — it will silently reintroduce this bug the moment it's reused anywhere `dynamicParams` isn't locked down (e.g. a search/lookup API route, ISR fallback, or a future refactor of `[slug]`).

**Fix:** Use `Object.prototype.hasOwnProperty.call()` (or a `Map`) to make the lookup safe regardless of how it's called:
```ts
export function getOfferingBySlug(slug: string): OfferingMetadata | null {
  if (!Object.prototype.hasOwnProperty.call(offerings, slug)) return null;
  return (offerings as Record<string, OfferingMetadata>)[slug];
}
```

### WR-02: Analytics event name collision hides which link was clicked on the Instagram offering card

**File:** `src/components/automate/OfferingCard.tsx:15-19, 40-51`
**Issue:** Every card wraps its title/tagline/description in a `Link` that fires `"Offering Card Click"`. The CTA link below it fires the *same* event name, `"Offering Card Click"`, whenever `offering.hasLiveCheckout` is true (currently only the Instagram offering):
```tsx
onClick={() =>
  trackAnalyticsEvent(
    offering.hasLiveCheckout ? "Offering Card Click" : "Waitlist CTA Click",
    { offering_id: offering.id }
  )
}
```
Both links navigate to different destinations (`/automate/${offering.id}` for the title vs. `offering.ctaHref` for the CTA), but with identical event name + props there is no way to tell from analytics whether a user clicked the card body to read more or clicked the CTA intending to check out. This defeats the purpose of tracking CTA clicks separately from card-browse clicks for the one offering where that distinction (browsing vs. converting) matters most.
**Fix:** Give the live-checkout CTA its own event name, e.g. reuse the existing `"Checkout Opened"` event (already declared in `analytics.ts`) or add a distinct one:
```tsx
onClick={() =>
  trackAnalyticsEvent(
    offering.hasLiveCheckout ? "Checkout Opened" : "Waitlist CTA Click",
    { offering_id: offering.id }
  )
}
```

### WR-03: Hardcoded offering count in the back-link text

**File:** `src/app/automate/[slug]/page.tsx:51-55`
**Issue:**
```tsx
<Link href="/automate" className={styles.backLink}>
  See all 5 automations
</Link>
```
The `5` is a literal that isn't derived from `getAllOfferingsSlugs()` (already imported/available from `@/lib/checkout`). It happens to match today's catalog size, but the next offering added or removed won't update this copy — it will silently go stale, unlike every other place in this phase that sources counts/labels from `checkout.ts`.
**Fix:**
```tsx
import { getAllOfferingsSlugs } from "@/lib/checkout";
...
See all {getAllOfferingsSlugs().length} automations
```

## Info

### IN-01: `CatalogGrid` is marked `"use client"` without needing client-only APIs

**File:** `src/components/automate/CatalogGrid.tsx:1`
**Issue:** `CatalogGrid` itself only maps over static `offerings` data and renders `OfferingCard` (which is already its own `"use client"` component for its `onClick` handlers). Marking `CatalogGrid` as a client component forces its subtree to hydrate client-side unnecessarily; it could stay a server component and let `OfferingCard`'s own boundary handle interactivity.
**Fix:** Drop the `"use client"` directive from `CatalogGrid.tsx` — `OfferingCard`'s boundary is sufficient.

### IN-02: `offerings.instagram` carries unused/duplicated hero and FAQ fields

**File:** `src/lib/checkout.ts:144-161`
**Issue:** `offerings.instagram` defines `heroHeadline`, `heroSubheading`, `scopeConstraint`, and `faqs: []`, but `/automate/instagram/page.tsx` never reads `getOfferingBySlug`/`offerings.instagram` for its hero or FAQ content — it hardcodes its own `<HeroSection>`/`<FAQSection>` components instead. `heroHeadline` in `checkout.ts` ("Instagram Lead Automation for Creators") duplicates the page's own `metadata.title`, so the two copies can drift independently with no compiler or test tying them together.
**Fix:** Either wire `/automate/instagram` to read hero copy from `offerings.instagram`, or trim the unused fields (`heroHeadline`, `heroSubheading`, `scopeConstraint`, `faqs`) from the Instagram entry to avoid a second source of truth. Non-blocking, but worth a follow-up.

### IN-03: `OrderNotification`'s product-name lookup can silently render `undefined`

**File:** `src/emails/OrderNotification.tsx:18-22`, `src/app/api/paddle/webhook/route.ts:21-24`
**Issue:** The webhook derives `productType` with a fallback of the literal string `'unknown'`:
```ts
const productType =
  event.data.items?.[0]?.price?.custom_data?.product ??
  event.data.custom_data?.product ??
  'unknown';
```
`sendOrderNotificationEmail`/`OrderNotification` type `productType` as the strict union `"dfy" | "dwy" | "care-plan"`, but because `event.data` comes from `JSON.parse` (typed `any`), TypeScript doesn't catch the mismatch. If a webhook payload arrives without `custom_data.product` (e.g. a checkout not wired through `PaddleCheckout`'s `customData` prop), `productType` becomes `"unknown"`, and `PRODUCT_NAMES[productType]` in the email template resolves to `undefined`, rendering "Product: undefined" in the owner notification email instead of failing loudly or falling back to something readable.
**Fix:** Either narrow/validate `productType` before sending (log + skip email construction if it's not one of the three known values), or give `PRODUCT_NAMES` a defined fallback:
```ts
Product: {PRODUCT_NAMES[productType] ?? productType}
```
