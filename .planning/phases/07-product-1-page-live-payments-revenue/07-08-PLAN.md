    - verifyPaddleWebhookSignature(body, signature, secret) returns false when signature is malformed (missing "ts=" or "h1=" segments) — never throws

  <action>
    Create `src/lib/paddle-webhook.ts` exporting `export function verifyPaddleWebhookSignature(body: string, signature: string, secret: string): boolean`. Parse the Paddle `paddle-signature` header format `ts=<unix_ts>;h1=<hex_hmac>` (split on `;`, then each segment on `=`). Compute `crypto.createHmac('sha256', secret).update(`${ts}:${body}`).digest('hex')` and compare against `h1` using `crypto.timingSafeEqual` (not `===`, to avoid timing side-channel — wrap in a try/catch since timingSafeEqual throws on length mismatch, returning false in that case). Reject (return false) if `Math.abs(Date.now() / 1000 - Number(ts)) > 300` (5-minute replay window). Wrap the whole function body in try/catch returning false on any parse error — this function must never throw.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Internet → `/api/paddle/webhook` | Unauthenticated POST endpoint; only the HMAC signature distinguishes genuine Paddle traffic from spoofed requests |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|--------------|-----------------|
| T-07-10 | Spoofing | `/api/paddle/webhook` POST body | mitigate | HMAC-SHA256 signature verification via `PADDLE_WEBHOOK_SECRET`, constant-time comparison (`crypto.timingSafeEqual`), rejects any request without a valid signature |
| T-07-11 | Tampering | Replay attack (captured webhook resent) | mitigate | Signature payload includes a timestamp; requests older than 5 minutes are rejected regardless of valid HMAC |
| T-07-12 | Repudiation / Duplicate processing | Webhook retries (Paddle retries up to 60x over 3 days on non-2xx) causing duplicate order processing | accept | No database exists in this codebase (confirmed in RESEARCH.md Environment Availability) so transaction-ID-keyed idempotency cannot be persisted server-side in this phase. Accepted risk: duplicate `transaction.completed` deliveries may cause a duplicate confirmation email (Plan 11) rather than a duplicate charge (Paddle, not this code, owns the charge). Mitigated by always returning 200 promptly on any successfully-verified request, which minimizes Paddle's retry frequency. Documented here for a future phase to add DB-backed idempotency if duplicate emails become a real support burden. |
| T-07-13 | Denial of Service | Unbounded POST body / high-frequency spoofed traffic | accept | Vercel serverless default limits apply; no additional rate limiting added in this phase (same accepted-risk class as T-07-07) |
</threat_model>
